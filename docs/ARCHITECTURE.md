# Архитектура: из чего состоит бот и как всё связано

Документ для разработчика или техника, который хочет понимать, что появится на
сервере, какие процессы будут крутиться, куда бот ходит по сети и что пишет на
диск. Развёртывание по шагам: [`SETUP.md`](SETUP.md). Ежедневное владение:
[`OPERATIONS.md`](OPERATIONS.md). Карта модулей: [`../bot/README.md`](../bot/README.md).

## 1. Одним абзацем

Telegram-бот, который отвечает сотрудникам на вопросы по базе знаний, пополняет
базу по их словам и из рабочих чатов и хранит всё в git-репозитории. База знаний
является папкой Markdown-файлов (`knowledge/`), а не СУБД. Модель вызывается через
OpenRouter, векторного поиска нет: модель получает каталог заголовков и сама выбирает,
какие единицы прочитать. Один Python-процесс в одном Docker-контейнере, без входящих
портов, без базы данных, без cron.

## 2. Что стоит на сервере

| Компонент | Где | Примечание |
|---|---|---|
| Клон git-репозитория | `/opt/kb-bot` | база знаний, код, поток чатов; бот пишет сюда и коммитит |
| Docker-образ | `python:3.12-slim` + git + openssh-client + tzdata + пакеты из `requirements.txt` | около 400 МБ |
| Контейнер `kb-bot` | `restart: unless-stopped`, healthcheck | около 200 МБ памяти, CPU близок к нулю в покое |
| Docker-том `kb-bot-data` | в контейнере `/app/data` | логи, переписка, живое состояние, кэш; единицы мегабайт |
| Секреты | `/opt/kb-bot/bot/.env` | токен Telegram, ключ OpenRouter; в git не попадает |
| Deploy-ключ GitHub | `/root/.ssh/id_ed25519_github`, `config`, `known_hosts` | монтируются в контейнер только на чтение |

Хватит 1 vCPU, 1 ГБ памяти и 10 ГБ диска.

Имя compose-проекта берётся от папки `bot/`, поэтому том называется `bot_kb-bot-data`.
Если на хосте уже есть проект `bot`, задайте `COMPOSE_PROJECT_NAME` в `.env`.

## 3. Сеть

Входящих портов нет. Бот работает по long polling: сам опрашивает Telegram. С другими
проектами на том же хосте не конфликтует ни по портам, ни по сети.

| Куда | Зачем | Как часто |
|---|---|---|
| `api.telegram.org:443` | получение сообщений, ответы, кнопки, файлы | постоянно |
| `openrouter.ai:443` | вызовы модели: ответы, классификатор, ночной разбор, правки | на каждый вопрос и по расписанию |
| `github.com:22` | `git pull --rebase` и `git push` | при каждой правке базы и раз в сутки пачкой |

Без GitHub бот продолжает работать: правки хранятся в локальном клоне, а руководители
раз в сутки получают сигнал «правки не уезжают в git». Без OpenRouter бот не отвечает.
Без Telegram ждёт, через 15 минут перезапускает сам себя.

## 4. Репозиторий: кто куда пишет

```
knowledge/          база знаний: разделы с единицами *.md, INDEX.md (каталог),
                    PEOPLE.md (кто за что отвечает), LINKS.md (ссылки),
                    _config.json (профиль компании и разделы), _gorizont.md
files/              библиотека файлов: бинарник + карточка *.md с описанием
chats-live/         поток рабочих чатов: <chat_id>/<YYYY-MM>.jsonl
bot-state/          state.json, суточный снимок состояния бота
bot/                код, Dockerfile, docker-compose.yml, .env (не в git)
docs/               документация и сценарные прогоны
```

| Папка | Пишет бот | Пишет человек | Уходит в git |
|---|---|---|---|
| `knowledge/**` | да: по подтверждению автора и ночным разбором | да, руками; бот заметит в течение минуты | сразу, один коммит на правку |
| `files/` | да: загрузка через Telegram | да | раз в сутки пачкой |
| `chats-live/` | да, непрерывно | никогда | раз в сутки пачкой |
| `bot-state/` | да: снимок при суточной публикации | нет | раз в сутки пачкой |
| остальное | нет | да | вручную |

Git-личность бота: `user.name=KB Bot`, `pull.rebase=true`. Его коммиты начинаются с
«База (бот):», «Сырьё (бот):», «Ссылки (бот):».

## 5. Docker-том: что бот пишет о себе

| Файл | Что это |
|---|---|
| `bot.log` | лог, ротация 5 МБ × 3 |
| `state.json` | живое состояние: руководители, доступы, чаты и топики, модель, автозапись, очередь ночного разбора, журнал автозаписей, подписи «@ник → имя» |
| `transcripts.jsonl` | переписка сотрудников с ботом в личке: вопрос, ответ, использованные единицы |
| `usage.jsonl` | расход токенов и денег по каждому вызову модели |
| `feedback.jsonl` | оценки ответов |
| `suggestions.jsonl` | идеи сотрудников |
| `dialogs.json` | текущие разговоры: переживают перезапуск, забываются через 12 часов |
| `answer_cache.json` | кэш ответов, до 500 записей, 30 дней |
| `heartbeat` | отметка живости для healthcheck |

Всё это намеренно не в git: вопросы сотрудников личные, а репозиторий читает всякий,
у кого есть доступ к коду. Если том пустой при первом запуске, бот восстанавливает
`state.json` из снимка `bot-state/state.json`: роли и чаты не теряются, теряется
только переписка.

## 6. Процессы внутри контейнера

Один процесс `python main.py`: цикл long polling и пять фоновых задач на asyncio.

| Задача | Период | Что делает | Модуль |
|---|---|---|---|
| Publisher | проверка раз в час | раз в сутки: снимок состояния, `git add files chats-live bot-state`, commit, `pull --rebase`, `push` | `publisher.py` |
| DailyDigest | раз в 10 минут | 21:00 ночной разбор чатов и автозапись; понедельник 10:00 недельный отчёт; 10:00 напоминание о гипотезах с прошедшей контрольной точкой; закрытие пунктов очереди старше 14 дней | `daily.py`, `autonomy.py` |
| Heartbeat | раз в 60 секунд | `get_me()` к Telegram и отметка в томе; отметка старше 180 секунд означает «нездоров»; 900 секунд без связи приводят к `sys.exit`, и Docker перезапускает контейнер | `heartbeat.py` |
| Alerts | раз в 5 минут | считает подряд идущие сбои модели и git, меряет диск; пишет руководителям не чаще раза в сутки на каждый вид сигнала | `alerts.py` |
| Watch | раз в 60 секунд | отпечаток файлов `knowledge/`; изменились мимо бота (git pull, правка руками), значит перечитать базу и сбросить зависимые ответы из кэша | `main.py` |

Docker healthcheck каждые 60 секунд запускает `healthcheck.py`, который смотрит на
свежесть heartbeat. Проверяется не «процесс жив», а «Telegram отвечает»: зависший
long polling иначе выглядел бы снаружи как тихий день в чатах. Часовой пояс
контейнера задаётся в `docker-compose.yml`, все расписания считаются в нём.

## 7. Как рождается ответ

```
сообщение в Telegram
  → роль? нет доступа: отказ и заявка руководителям
  → классификатор типа запроса (дешёвая модель, одно слово: факт / разбор / возражение / файл / прочее)
  → агент: системный промпт + INDEX.md + PEOPLE.md + LINKS.md   ← этот префикс кэшируется у провайдера
      инструменты: get_kb_units(id…), search_kb(слова), find_files, request_file
      до 6 кругов «модель → инструмент → модель»
  → формат по типу: факт коротко, разбор по шагам, возражение как суть + фраза клиенту
  → на возражениях: сверка фразы для клиента с текстом единиц (factcheck)
  → кэш ответов (ключ: вопрос + единицы, на которых построен ответ)
  → transcripts.jsonl, usage.jsonl, bot.log
```

Почему так:

- **Каталог вместо векторного поиска.** На сотнях единиц модель выбирает тему по
  заголовкам точнее, чем эмбеддинги по коротким вопросам, и это не требует ни
  индекса, ни отдельной инфраструктуры. Цена: каталог идёт в каждый запрос, поэтому
  системный блок собирается детерминированно и кэшируется у провайдера. Любой
  меняющийся байт в начале промпта обнуляет кэш, поэтому дата и время добавляются
  в конец.
- **Классификатор отдельным вызовом.** Задача простая, ответ одно слово, платить за
  неё по цене основной модели незачем. Если классификатор не ответил, бот пробует
  основную модель, а затем отвечает по самому мягкому формату.
- **Сверка фразы для клиента.** Фраза уходит клиенту дословно, и выдуманная цифра
  в ней стоит дороже, чем ещё один дешёвый вызов. При расхождении бот дописывает
  предупреждение и ничего не переписывает сам.
- **Кэш ответов по вопросу и единицам.** Похожие, но разные вопросы в один ключ не
  сходятся. Правка единицы сбрасывает все ответы, построенные на ней.
- **Честность.** Бот не видит таблиц, CRM и панелей, только базу. Промпт запрещает
  расшифровывать `@ник` в имя, если пары нет в `PEOPLE.md`: иначе модель
  достраивает имена по смыслу.

## 8. Как бот пишет в базу

Два пути, различие одно: видел ли человек формулировку перед записью.

1. **По просьбе человека, с подтверждением.** «Запомни: …», кнопка «Внести в базу»,
   пересланное сообщение, тег бота в рабочем чате. Бот подбирает единицу по каталогу
   (до трёх кандидатов, затем «скептик» выбирает по тексту), готовит правку,
   перепроверщик откатывает всё постороннее, автор видит итоговый текст и жмёт
   «верно». Чужое нажатие не считается. Запись получает подпись `*(внёс Имя, дата)*`
   и уходит одним коммитом с push сразу. Черновик без ответа живёт сутки.
2. **Ночной разбор чатов, без человека.** Бот читает поток рабочих чатов за сутки
   (телефоны, почты и чужие домены вычищает код, `scrub.py`), достаёт факты и
   записывает то, что может: с оговоркой «не подтверждено», рискованное (цифры,
   слова клиенту, новые темы) ещё и со `status: needs-check`. Лимит 10 записей в
   сутки. Что записать не смог, кладёт в очередь на решение руководителю, она сама
   закрывается через 14 дней. Всё записанное попадает в недельный отчёт с кнопкой
   отката (`git revert`). Через 30 дней без возражений оговорка снимается сама
   (`aging.py`).

Жёсткие правила автомата заданы в коде, а не в промпте (`autonomy.hard_rules`):
существующий текст никогда не удаляется и не переписывается, `needs-check` автомат
не снимает, противоречие записанному он не разрешает. Противоречие вскрывается
позже, когда сотрудник получил ответ, не согласен и диктует, как правильно.

Смена значения удалением не считается: у единицы с блоками «Сейчас» и «Было раньше»
код сам уводит прежнее значение в историю с датой. Ключ строки строгий
(`- **Ключ:** значение`), потому что именно по ключу код находит, что заменять,
а искать «строку про то же самое» модель умеет плохо.

Шапку новой единицы (id, дата, источник) собирает код, не модель: иначе id может
оказаться занятым, а источник выдуманным. Id из диапазона раздела, заданного в
`knowledge/_config.json`. Счётчики в `INDEX.md` бот поддерживает сам, `selfcheck.py`
проверяет, что они сходятся. Перед записью бот сверяет каталог с диском: если
`INDEX.md` изменился с момента подготовки правки, запись отменяется, а не затирает
чужую строку.

## 9. Слушатель рабочих чатов

Бота добавляют в рабочий чат (Group Privacy в BotFather выключен, иначе он не видит
сообщения). Он молчит и не записывает, пока руководитель не ответит в личке:
«рабочий, записывать» или «клиентский, нет». Записываемые чаты пишутся в
`chats-live/<chat_id>/<YYYY-MM>.jsonl` (поля: `at, chat_id, chat_title, thread_id,
topic, message_id, user_id, user_name, username, kind, text`). Топики форумов
различаются и заглушаются по отдельности. В записываемых чатах бот отвечает на
упоминание или реплай, подкладывая последние 10 сообщений того же топика как контекст.

Реакции на сообщения Telegram отдаёт только если бот администратор чата. Файлы из
чатов не скачиваются.

## 10. Роли, доступ и состояние

Ролей две. **Менеджер** спрашивает, диктует в базу, добавляет файлы и ссылки.
**Руководитель** дополнительно управляет доступами, чатами, моделью, откатывает
автозаписи и назначает руководителей. Всё управление из меню бота. Роли хранятся в
`state.json` тома и в суточном снимке `bot-state/state.json`.

`LEADER_IDS` в `.env` нужен только для самого первого запуска на пустом томе без
снимка и для аварийного входа: каждый ID импортируется в состояние один раз, дальше
источник правды сам бот. Снятый из бота руководитель не возвращается после
перезапуска, даже если остался в `.env`. Роль руководителя выдаётся только по
числовому ID: ник переназначаем, и освободившийся ник мог бы перехватить посторонний.

Руководителям бот пишет первым только в семи случаях: заявка на доступ, новый чат,
недельный отчёт, три критичных сигнала, смена состава руководителей. Менеджерам
никогда.

## 11. Git: как бот и люди уживаются в одном репозитории

- Бот коммитит и пушит сам, поэтому deploy-ключу нужно право записи.
- Перед push бот делает `git pull --rebase`; при конфликте `rebase --abort` и сигнал
  через alerts после трёх сбоев подряд.
- Файлы `chats-live/*.jsonl` всегда грязные, они дописываются непрерывно. Поэтому
  клон на сервере обновляется только так: `git pull --rebase --autostash`.
- Правки `knowledge/` руками: коммит, push, бот подхватит в течение минуты через
  сторож файлов. Правки кода требуют `docker compose up -d --build`.
- Запись в файлы базы атомарная (временный файл и `rename`): обрыв процесса посреди
  записи не оставляет полупустой единицы или обнулённого состояния.

## 12. Проверки и тесты

Всё гоняется в отдельном контейнере, репозиторий монтируется только на чтение:

```bash
docker run --rm -e KB_ROOT=/app/kb -v /opt/kb-bot:/app/kb:ro -v /opt/kb-bot/bot:/app/bot bot-kb-bot python selfcheck.py
```

| Проверка | Нужны ключи | Что проверяет |
|---|---|---|
| `selfcheck.py` | нет | база, каталог, счётчики, разметка, модули по отдельности, агентский цикл на подставном провайдере |
| `python -m pyflakes *.py llm/*.py` | нет | неопределённые имена, которые selfcheck не ловит |
| `type_check.py` | да | классификатор типа запроса на наборе `test_types.txt` |
| `route_check.py` | да | маршрутизация правок в единицы, `test_updates.txt` |
| `answer_check.py` | да | качество ответов, `test_answers.txt` |
| `docs/scripts/menu_e2e.py` | нет | сценарии меню и передачи ролей на подставном боте |
| `docs/scripts/write_e2e.py` | да | путь записи на живой модели, в базу не пишет |
| `smoke.py "вопрос"` | да | один живой вопрос через боевую цепочку |

## 13. Ограничения

- Второй экземпляр бота с тем же токеном ломает long polling обоим: старый контейнер
  останавливать до запуска нового.
- Group Privacy у бота должен быть выключен.
- Реакции в чатах видны только администратору чата.
- OCR нет: скан без текстового слоя бот называет сканом.
- Build cache Docker растёт на каждом `--build`: `docker builder prune -af` время от времени.
- Каталог целиком уходит в каждый запрос: предел 300–400 единиц, см. [`SCALING.md`](SCALING.md).
