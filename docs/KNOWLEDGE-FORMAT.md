# Формат базы знаний

База знаний лежит в `knowledge/`: папка на раздел, файл на единицу, каталог
`INDEX.md`, справочник людей `PEOPLE.md`, ссылки `LINKS.md`, профиль компании
`_config.json`, словарь разделов, типов и тегов `_taxonomy.md`. Всё это обычный Markdown и JSON в git: править можно руками, бот
подхватит изменения в течение минуты после push.

## 1. Единица

Файл `knowledge/<раздел>/kb-NNN-<slug>.md` с YAML-шапкой:

```yaml
---
id: kb-203                      # уникальный; диапазон номеров закреплён за разделом в _config.json
title: Клиент говорит, что заявок нет
type: playbook                  # faq | reglament | case | playbook | template | article
section: klienty                # папка в knowledge/ и ключ в _config.json
tags: [заявки, лиды, возражение]
product: [Трафик]               # из products в _config.json, либо общее
status: actual                  # actual | needs-check | outdated
updated: 2026-08-14
horizon: rule                   # rule | experiment | incident, необязательно
sources:
  - со слов Анна Петрова (руководитель отдела), добавлено через бота 2026-08-14
---
```

Шапку единицы, созданной через бота, собирает код: id из свободного диапазона
раздела, дата записи, честный источник «со слов кого». Модель пишет только тело.

### Типы

| Тип | Что это |
|---|---|
| `faq` | короткий «вопрос → ответ» |
| `reglament` | внутреннее правило или порядок действий |
| `case` | разобранная конкретная ситуация: проблема → что сделали → итог |
| `playbook` | разбор повторяющейся ситуации с несколькими причинами |
| `template` | готовый текст клиенту |
| `article` | объясняющая статья по теме |

**Playbook** для вопросов, где ответ зависит от контекста («позиции упали»).
Структура: «Что уточнить перед ответом» (вопрос → к какому варианту ведёт ответ),
диагностика по шагам, варианты, у каждого «признаки → что делать → что сказать
клиенту». Бот задаёт уточняющие вопросы сотруднику и показывает только нужный
вариант, полная выкладка остаётся в файле.

### Статусы

| Статус | Когда |
|---|---|
| `actual` | подтверждено, действует |
| `needs-check` | спорное, привязанное к моменту, расходятся источники; всё, что бот записал сам из чатов и что рискованно (цифры, слова клиенту, новые темы). Снимает человек, либо пометка стареет сама через 30 дней без возражений |
| `outdated` | устарело; остаётся с пометкой, не удаляется |

### Правила содержания

- **В единице только правило.** Материал разбирательства (почему решили так,
  переписка, история ошибок) не кладётся: модель копирует то, что написано рядом,
  и устаревшая цифра в сноске превращается в «правило поменялось».
- **Простые факты в коротких единицах**, на которые playbook ссылается
  как на подстатьи: `[[kb-301]]`.
- **Изменения во времени не затираются.** См. блок «Сейчас» ниже.
- **Дата записи не равна дате события.** Что действует «с какого числа», пишется
  в самой строке факта.
- **Секреты и клиентские частности не переносятся:** пароли, коды доступа, ссылки
  на оплату, договоры конкретных клиентов, их телефоны и домены.
- **Подпись записи через бота:** `*(внёс Имя, дата)*` под текстом. Записи ночного
  разбора получают оговорку «не подтверждено».

## 2. Блок «Сейчас» и «Было раньше»

Единица хранит состояние, а не ленту событий. Там, где значение меняется, два блока:

```markdown
## Сейчас
- **Съём позиций:** ежедневно в 14:00 — с 01.08.2026

## Было раньше
- **Съём позиций:** ежедневно в 12:00 — по 31.07.2026
```

Новый факт не дописывается в конец, а заменяет строку про ту же сущность; старое
значение уезжает в «Было раньше» с датой, до которой действовало. Ключ обязателен
и строгий: `- **Ключ:** значение`. Именно по ключу код находит, что заменять. По
этой же форме бот собирает сводку «что действует сейчас» и отчёт «что изменилось
за период».

## 3. Горизонт единицы

Поле `horizon` в шапке говорит, чем единица является во времени:

| Горизонт | Что это | Дополнительные поля |
|---|---|---|
| `rule` | действующее правило (по умолчанию) | |
| `experiment` | гипотеза, которую проверяют | `control_point: 2026-09-15` дата, когда подвести итог; `closed: 2026-09-20` когда закрыли |
| `incident` | разовый случай, из которого сделали вывод | `happened: 2026-08-03` когда произошло |

Гипотезу без итога бот не оставляет молча: после контрольной точки напоминает
руководителю, а в меню «База → Гипотезы без итога» показывает открытые.
Незакрытый эксперимент через месяц иначе выглядит как действующее правило.

## 4. Каталог `INDEX.md`

```markdown
# Каталог базы знаний

14 единиц в 4 разделах. `⚠` — статус `needs-check`.

## produkt — Продукт (4)
- kb-101 · Как работает «Трафик»: что делаем и что обещаем [article]
- kb-102 · Сроки первых результатов ⚠ [faq]
```

Каталог целиком читает модель на каждый вопрос, поэтому заголовок единицы должен
отвечать на вопрос «о чём это» одной строкой. Счётчики в шапке и в заголовках
разделов проверяет `bot/selfcheck.py`, они должны сходиться с числом строк. Бот
поддерживает их сам, когда создаёт единицы.

## 5. `PEOPLE.md`

Кто за что отвечает: имя и зона ответственности, ничего больше. Ни характеров, ни
стиля речи, ни оценок: бот не подражает людям и не шутит про них. Файл нужен для
двух вещей: чтобы бот не выдумывал имена по нику и чтобы вместо «в базе этого нет»
мог сказать, кто обычно отвечает на такие вопросы. Бот дополняет справочник
подписями «@ник → имя», которые видит в чатах, но подтверждённой частью считается
только этот файл.

## 6. `LINKS.md`

Рабочие ссылки, которые бот отдаёт по запросу. Строка на ссылку:

```markdown
- **Зум для планёрок отдела** — https://example.com/zoom · теги: зум, планёрка · добавил Анна, 2026-08-01
```

Добавляются через бота («запомни ссылку …») или руками. Сюда только постоянное,
разовые ссылки из чатов не тащим.

## 7. `files/`

Библиотека файлов: бинарник и рядом карточка `files/<имя>.md` с шапкой
(заголовок, теги, дата, кто добавил, описание). Бот сохраняет присланные файлы сам,
для pdf и docx извлекает текст и отвечает по нему. Путь всегда проверяется на выход
за пределы папки.
